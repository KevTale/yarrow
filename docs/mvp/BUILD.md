# Yarrow MVP — build brief (updated 2026-10-05)

This brief overrides the historical options in `synthese.md`. All prices and percentages marked _(hypothesis)_ are to be calibrated after launch.

## Principle

Yarrow is for **people who build software**: SaaS, games, tools, open source or closed source.
- **Project owners** connect their repo and tracker. Tagged tickets get processed **for free**, funded by sponsors.
- **Sponsors** fund the compute. In return they get visibility on the work they fund and on the leaderboard.
- The platform picks the work unit and delivers a reviewed PR or an explicit abstention.
- Agents run entirely on provider infrastructure: the platform hosts no execution environment.

**At launch, everything is free for project owners.** There is no paid plan. A paid offer (priority, extra features) will be designed later from real usage metrics and feedback.

### Product strategy

- **Differentiate where the labs won't:** a systematic cross-lab review (Claude implements, OpenAI reviews), the funding marketplace and frictionless onboarding.
- **Do not compete with the labs on agent context, memory or tooling.** They improve these continuously.
  - No custom "repo memory" system.
  - The agents read the project's own `AGENTS.md`, `CLAUDE.md` and `CONTRIBUTING.md` natively.
  - When a ticket is retried, the previous attempt and the owner's comments are passed as plain context (GitHub issues and, since 2026-10-14, Jira tickets: the last 20 comments, the builder's answers from Yarrow among them).

## Architecture (locked)

- **Shop:** TanStack Start on Cloudflare Workers. It handles the UI, auth, Stripe, webhooks and the dashboards.
- **Brain:** a Cloudflare Worker with a cron dispatcher (every minute) and one durable Workflow per run, with Postgres as the source of truth. It covers work unit selection, reserve/debit/release and PR creation.
  - **Kicked, not only polled** (decided 2026-10-10): the web Worker calls the brain's private `kick` (a service binding to its `Brain` entrypoint, unreachable over HTTP) whenever work is queued or money arrives: GitHub `issues` and `issue_comment` webhooks, Queue and Remove from queue on the dashboard, Retry, a ticket pasted and settled after connecting, a Jira project linked with its ticket, a settled Stripe payment. The pass runs GitHub tasks first (labeling, so an issue queued from Yarrow is labeled in seconds and its webhook kicks again), then the dispatch: a queued ticket starts within seconds. Each part takes a Postgres advisory lock so passes never overlap; a kick that finds a pass running retries a few times, 3 seconds apart. The minute's cron stays as the safety net (and runs the 5-minute tracker sync). The brain deploys before the web Worker, so the entrypoint exists when the binding does.
  - **Jira webhooks** (decided 2026-10-13): a `yarrow` label set in Jira itself queues the ticket in seconds, like a GitHub one. Each Jira connection holds one dynamic webhook (Jira allows 5 per app, user and site) on its linked projects (`project in ("APP", "WEB")`; Jira's webhook JQL cannot filter on labels, so Yarrow reads the ticket again and decides), for issues created, updated (labels, status, summary, description only) and deleted. Linking or unlinking a Jira project moves it at once; the brain checks every connection once an hour (minute 30) and refreshes a webhook with less than 20 days left of Jira's 30, or registers it again when Jira no longer has it. Deliveries reach `/api/webhooks/jira`, signed by Jira with a JWT (HS256, the app's client secret). The webhook belongs to the person who connected Jira: their access gone, it stops. It needs the `manage:jira-webhook` scope, asked at Connect from now on; a connection made before, or any refusal, is kept on the connection (`webhook_error`) and never blocks linking. Jira only delivers a non-public OAuth app's webhooks when its owner registered them, so the Atlassian apps must be shared (Distribution). The 5-minute sync stays as the safety net.
- **Hands:** provider-hosted agents, driven step by step by the run Workflow (`RunPipeline`):
  - **implements:** Claude Managed Agents (beta), Claude Code harness, Anthropic-hosted sandbox. Or, on dev since 2026-10-26 (Meta hackathon), Muse Code running Muse Wonder in a Cloudflare container of Yarrow's own (below).
  - **reviews:** OpenAI Agents API (beta), Codex harness, OpenAI-hosted sandbox.
- **Provider accounts:** platform-owned **API** accounts with prepaid credits. Never a consumer subscription (Claude Pro/Max, ChatGPT Plus/Pro).
- **Branding:** do not name the product or features after "Claude Code" or "Codex". "Powered by Claude" or "uses OpenAI models" is fine.
- **DB:** Supabase + Drizzle.
- **Environments:** local and `dev.yarrow.run` share the `yarrow-dev` Supabase project, Stripe test mode and the `yarrow-run-dev` GitHub App; `yarrow.run` has the `yarrow-prod` project and the `yarrow-run` App. Every push to `main` deploys dev, every push to `prod` deploys prod (GitHub Actions).
- **Design:** Opus dark ledger mockups (amber accent).
- **Out of the architecture:** Docker/Hetzner pool and OpenRouter. The Cloudflare container came in for Meta only, since Meta hosts models and no agents.

### Repository access and delivery

- The sandbox gets a **read-only**, short-lived GitHub App installation token, scoped to the single repo of the run.
- The agent returns a patch, a summary and evidence. It never pushes.
- The brain creates the branch, commit and **draft PR** through the GitHub App. This is the only write path.
- For tracker tickets, the brain comments on the ticket with the PR link.

### Fixed roles

- **Implementer:** Claude Opus 5.5, high effort, through Managed Agents.
- **Reviewer:** OpenAI Astra, through the Agents API.

Both are the same for every ticket. This is the platform's offer. Model IDs and effort are server-side config, so they can follow model releases.

**Meta as implementer** (decided 2026-10-26, for the Meta hackathon; dev only). The dev brain's `IMPLEMENTER` secret picks who implements the runs prepared from then on: `meta` or `claude` (the default, and production's). It is a secret rather than a variable of the config so that a deploy keeps it and switching takes seconds, with no push (decided 2026-10-27, the founder: Muse Wonder for the hackathon's demos, Claude Opus to move the product on): `pnpm implementer claude` or `pnpm implementer meta`; a run keeps the implementer it started with, since its session id says where it lives (`muse_<run>`). A project with test secrets stays on Claude (the container has no vault yet). Meta's Model API serves models only, so the run gets a container of its own (`workers/muse.ts`, Cloudflare Containers, a Durable Object per run, `standard-3`): the repository cloned at `/workspace/repo`, the recorder at Claude's path, Muse Code (`muse exec --json --yolo`, contributor mode off, web tools off) with the same rules, task, outputs and fix rounds as Claude (`--session-id` resumes the conversation). The container has no Internet of its own: a Worker sees every request, adds the Meta key to Meta's (Muse Code calls it in plain HTTP, the Worker goes on in HTTPS) and the run's read-only token to GitHub's, lets the package registries and `SANDBOX_HOSTS` through and refuses the rest; no key ever enters the container. Meta reports no cost: the Worker counts each answer's tokens per model as it completes (Wonder, and Spark for Muse's side tasks), priced at list price, plus the container's time (CPU counted busy throughout). The container stops when the run settles, or 90 minutes after its last request. The feed comes from Muse's events (files read and edited, commands and tests), read by the brain as it polls; a viewer's request does not reach the container. The admin's compute shows Meta's spend apart; Meta has no out-of-credit pause yet: its runs fail instead.

Run cost = tokens + sandbox/container time, measured from provider usage data and written to the ledger in cents.

## Project owners

### Onboarding

Least friction first (decided 2026-10-06): one "Connect GitHub" from the landing, nothing typed that the repo already says.

1. Sign in with GitHub, then install the GitHub App on the chosen repositories ("all" or a selection, private ones included). Installing requires repo admin rights, which proves control.
2. One project per selected repository is created automatically: name, description, languages and default branch come from the repo. Every other field is optional and editable later.
3. Yarrow creates the `yarrow` label on each repository.

How it runs: "Get a pull request" and "Connect" go to `/connect/github` (GitHub sign-in, then the App install; the pasted ticket waits in a short-lived cookie). The signed `installation` webhook creates the projects in the installer's account: public repos are Public, private repos are Listed, repositories already on Yarrow are skipped. GitHub then returns the owner to the App's Setup URL, `/connect/done`, which queues the pasted ticket once its repository is connected. GitHub writes (creating the label, labeling the pasted ticket) are `github_tasks` carried out by the brain's cron; labeling the ticket is the owner's authorization, and the issues webhook queues it. Repo description, homepage, default branch and top languages fill only the fields the owner left empty.
   - **Back without the pasted repository** (decided 2026-10-12): it was not picked during the install, or it is not the visitor's to install (only a repository's admins can, so an issue pasted from someone else's project ends here). Once projects are there and the repository is still missing three polls (about 9 s) after the install, or after a minute in any case, the dashboard shows "owner/repo is not connected · Only its admins can add it" with **Add it on GitHub** (back through `/connect/github` with the ticket), and a close that forgets the ticket. Polling goes on behind it for the minute, so a late webhook still queues the ticket. A member who is not an organization's admin only asks them: GitHub returns `setup_action=request`, and the dashboard says "Request sent · owner's admins approve it on GitHub". Once approved, the projects land in the approving admin's account, not the requester's.
4. Optionally connect a tracker and map each board to its repo. Supported trackers: GitHub Issues, Linear, Jira and Trello.
5. Tag tickets with the platform label (`yarrow`) or the tracker's equivalent. Only tagged tickets become work units.
6. Nothing to describe for the presentation (decided 2026-10-16): the agent finds how to run the app and keeps that recipe for the next run (see Evidence). What follows stays possible, though no screen asks for it yet:
   - Setup and start commands, plus a seed.
   - Development environment variables.
   - **Test or staging secrets only, never production.**
   - Secrets are stored write-only and encrypted. They are injected through the providers' vault mechanisms, so the agent never sees the values. A secret can only be used for HTTP calls to allowed hosts.
   - Apps that need a database use the one preinstalled in the sandbox, with the seed.

All four trackers are built. Until each has run live, the landing marks Linear and Trello as "soon" (decided 2026-10-07).

**Next sources (decided 2026-10-28):** Linear first, then Trello; GitLab and Azure DevOps only when a builder asks, since a team on either keeps its code there too, which means a second code host (branch, commit, merge request, merge), not one more tracker.

**Jira (decided 2026-10-08):** Jira holds the tickets, GitHub holds the code; GitHub stays the only code host (GitLab, Bitbucket and Azure DevOps would each need their own branch, commit, PR and merge plumbing, later and on demand). The landing offers Jira as soon as the deployment has its Atlassian OAuth app. The builder's journey:
1. Paste a Jira link (`acme.atlassian.net/browse/APP-42`, or a board link with `selectedIssue=`), or choose Jira and Connect.
2. GitHub first, as for every source: sign in and install the App. A builder who already has a connected repository skips it.
3. The dashboard shows a Jira card: the key, the site, and **Code in** (the repository). Without Jira yet: **Connect Jira** (Atlassian's consent, then back to the dashboard). With Jira: **Queue it** (or **Link** without a pasted ticket, with the Jira project to choose).
4. The Jira project (its key, `APP`) is linked to that repository, and the pasted ticket gets the `yarrow` label in Jira and enters the queue. Later pastes of `APP-*` tickets go straight to the queue.
5. The project's table lists its Jira tickets next to its GitHub issues (`APP-42` with Jira's blue mark); Add to queue and Remove put and take the label in Jira at once; labels set in Jira itself are picked up by the 5-minute sync.
6. Moves on the board (decided 2026-10-08): under each linked Jira project, the settings page sets where tickets move when Yarrow starts, when the PR opens and when it is merged, among the project's own statuses (columns follow statuses; names as the team wrote them) or "Don't move". Defaults are proposed once, without AI: started → the first "in progress" status that is not a review, PR → a status whose name reads like a review, if any, merged → don't move (many teams close after shipping). A fourth event, Yarrow stopped (the run abstained), is the builder's call too, and the only move allowed to go backwards: by default **back where it was** (decided 2026-10-28, the founder: a ticket Yarrow moved to "in progress" and dropped made the board say someone was on it). Yarrow keeps the status the ticket had when it moved it on starting, and puts it back there when it stops; nowhere when Yarrow had not moved it (a person had put it further). The settings offer "Back where it was", "Don't move" or a status. No "stopped" column is made in the tracker: what is asked of the team is in Yarrow's comment on the ticket, and in Yarrow the ticket sits in Stopped, not To do, since it waits on someone. Moves saved before that day held "Don't move" there as the old default, never chosen, and were turned to "Back where it was". The brain moves the ticket at start and when the PR opens, the GitHub webhook when it is merged; a ticket never moves backwards, and a move the workflow refuses never blocks the work and shows on the settings page. The boards API (real column names) was set aside: reading a board's configuration needs Jira admin rights.
7. Delivery: the branch and the PR title keep the key in capitals (`yarrow/APP-42-…`, `APP-42 Fix…`) so Jira links them to the ticket, and Yarrow comments on the ticket with the PR.

One Jira project maps to one repository. Teams with one Jira project for several repositories wait for a V2 (for example, the repository chosen by the ticket's Component). Jira sites are named by their address (`acme.atlassian.net`).

**Linear (decided 2026-10-28):** as Jira, wherever Jira goes. A team is a board, named by its key (`ENG`), and a ticket by its identifier (`ENG-42`), which Linear's API reads as well as its id; that is how a ticket finds its board, and the identifier in the branch and the PR title is how Linear's GitHub integration links them, so the PR title keeps it. The settings page connects Linear and picks the teams whose tickets the repository takes, then where tickets move as Yarrow works, among the team's own statuses (Linear lets a ticket go to any of them; never backwards, except Yarrow stopped). The dashboard lists the teams' open tickets beside GitHub's issues with Linear's mark, puts and takes the `yarrow` label (created for the team the first time, a workspace label of that name used when there is one), writes new tickets there in Markdown as the person who connected Linear, answers the agents' questions as comments, and closes tickets to the team's first completed status. The agents read the ticket's last 20 comments. Linear's access tokens last 24 hours since April 2026: Yarrow keeps the refresh token and refreshes like Jira's. The webhook is set once in the Linear OAuth app's settings (`/api/webhooks/linear`, Issues, its signing secret as `LINEAR_WEBHOOK_SECRET`) and reaches Yarrow for every workspace that allowed the app; deliveries are checked by signature and must be under a minute old; the 5-minute sync stays as the safety net. No Linear card on the dashboard for a pasted link: pasting is leaving the landing (below). Linear stays "soon" on the landing until it has run live.

Later: appear as an assignable agent in Linear and Jira, so owners can simply assign a ticket to "Yarrow".

### Visibility tiers (chosen by the owner, all free)

| Tier | Public view |
| --- | --- |
| **Public** | Code and PRs (open source) |
| **Listed** | Name, description, product URL, shipped work count. No code, no PRs |
| **Hidden** _(final name TBD)_ | Nothing. It only appears as "a private project" in aggregate stats |

- Hidden projects are funded like any other: "Every project" includes them (decided 2026-10-07; Listed projects already show no code or PRs, so an opt-in added a choice without meaning).
- Code is never shown to the platform team or to sponsors. Only the providers process it, through their API under commercial terms. Sandboxes are destroyed after each run.
- Ticket text and project descriptions are processed by the platform for triage and moderation (see Trust & safety). The terms say so.

## Sponsors

### Why sponsors pay

- **Advertisers:** companies selling to builders (dev tools, infrastructure, AI). They reach people actively shipping products, can target by stack, and get reporting: "your €500 shipped 140 tasks in 38 products".
- **Fans:** users of a product who fund its roadmap. Each project gets a shareable "Fund our roadmap" badge, so project owners bring their own sponsors.
- **Patrons:** individuals who like supporting builders.

The leaderboard is the game layer on top.

### Sponsor filters

- Two choices in the sponsor's Settings (decided 2026-10-07):
  - **Every project** (`all_except`, default): new projects are included automatically.
  - **Only the projects I choose** (`only`): a searchable list opens right under the option; new projects are **not** included.
- The ledger still supports excluded categories and required stacks, but the UI no longer offers them: projects created from GitHub have no category.
- If none of the selected projects has an eligible ticket, the credit stays unused. The dashboard says so.

### Launch and outreach

- **Founding pool, target $20,000**, raised from the founder and real founding sponsors. It is shown transparently as such.
- Founding sponsors get a permanent "Founding sponsor" badge and a reduced margin for life _(hypothesis)_.
- **No fake accounts or simulated activity.** The leaderboard and feed show only real money and real runs.
- **Daily fundings** (decided 2026-10-10): so that Today is never empty while Yarrow starts, the founder funds the sponsor rows of their own other projects every day, as any sponsor would, with real money spent on real runs. The credit skips Stripe (no fee, no tax, no margin): a `daily_fundings` row (user, amount, window) makes the brain's cron add a settled `direct` contribution once per UTC day, idempotent through `contributions.direct_key`. Direct credit ranks on the boards like a card payment; the account page lists it as "Direct", with no invoice. They are managed in the admin (below): a sponsor row with no account behind it, its amount per day (a credit already landed stays as it was), its window, pause and resume (a day is never credited twice).
  - **Each lands at its own time** (decided 2026-10-12): sponsors all arriving at midnight would read as staged. Each row has a window in UTC, from and to (00:00–00:30 by default; the founder sets, say, 05:00–09:00 and 11:30–18:00 for the others), and the credit lands at a minute drawn in it, a new draw every day (a hash of the sponsor and the date, so every tick of the day agrees and nothing is stored). The cron looks every minute. The admin shows the window and today's minute ("Lands at 07:42 UTC") until it lands.
  - **Add now or Schedule** (decided 2026-10-12): a new sponsor row is added with one of two buttons. **Add now** credits today at once, whatever the window (the cron's key for the day, so the day is still credited once); the window applies from tomorrow. **Schedule** leaves it to the cron: today at its drawn minute if that minute is still to come, otherwise from tomorrow, so a credit never lands outside its window ("Lands tomorrow at 07:42 UTC" until then).
  - **A day's credit is for that day** (decided 2026-10-12): at midnight UTC what a daily funding left unspent expires (`expireDailyCredit`: the contribution's credit comes down to what was reserved and debited, with a `contribution.expired` event, as a refund freezes credit), so quiet days never pile up a balance that a burst of tickets could spend on the founder's provider accounts: the most the founder pays a day is the sum of the amounts, and usually what was run. Compute a run at work holds stays until it settles; what it releases then expires at the next pass. The boards and the admin count what was put in (`amount_cents`), not what is left. Only the daily fundings expire: card payments and promo credit stay until spent.

### Admin

Decided 2026-10-10: a separate Worker, `workers/admin.ts`, on admin.yarrow.run (admin-dev.yarrow.run for dev), rather than a route of the web app, so that nothing of it is reachable from the public site. Cloudflare Access stands in front (Zero Trust team `aged-lake-dc6c`, one application per domain, the founder's email only, by an emailed code or the Cloudflare login, sessions of 30 days, strict same-site cookie); the Worker checks Access's signed token itself as well (issuer, audience, expiry, email) and answers 404 to anything else, and refuses forms posted from another origin. It holds no secret: every read and write goes through the brain's `Admin` entrypoint over a service binding. A server-rendered page, no client bundle. One page: **Compute** (decided 2026-10-11), each provider's spend today, over 7 and 30 days (Anthropic as reported, OpenAI priced by Yarrow, marked ≈), its pause with the provider's words and Resume, the sponsor credit left by source (card, direct, promo) and the run cost no sponsor money covered over 30 days; then the daily fundings. Moderation, project suspension, failed runs and refunds come when they are needed.
- Outreach order:
  1. a working demo on real projects (the founder's own and friends') with real PRs;
  2. individuals from the founder's network;
  3. mid-size builder-facing brands (founders reachable on X, tens of thousands of followers);
  4. large brands, once there are metrics.

  Before launch, ask for **pledges** that convert to payment at launch rather than upfront payment. Announce each founding sponsor publicly as social proof for the next one.

## Money

- **Sponsor packs:** $10 / $25 / $100, plus a **custom amount** in whole dollars between $10 and $1,000. The minimum avoids fixed Stripe fees eating small payments. The maximum limits fraud and chargeback exposure in v1.
- **Platform margin:** 7.5% of sponsor money excluding VAT _(hypothesis; lowered from 10% on 2026-10-09)_. It is the only revenue at launch.
- **Compute credit** = amount paid excluding VAT − actual Stripe fee − platform margin.
  - The Stripe fee comes from the Stripe balance transaction in the webhook, never from an estimate.
  - The fund page shows the business estimate (fees, margin, compute credit) with "VAT included where it applies"; no consumer toggle (decided 2026-10-07). Examples for $100:
    - a business (no VAT), US card: about $3.20 Stripe and $7.50 margin, so about **$89.30 compute**;
    - a French consumer, VAT-inclusive: $83.33 excluding VAT, about $3.20 Stripe and $6.25 margin, so about **$73.88 compute**.
- **VAT** is handled with Stripe Tax:
  - EU consumers pay VAT at their country's rate (prices shown VAT-inclusive);
  - EU businesses with a VAT number are reverse-charged.
- **Right of withdrawal:** EU consumers must give explicit consent to immediate start and acknowledge losing the 14-day withdrawal right before checkout. On the landing it is the second box of the payment dialog, "Compute starts right away: I give up my 14-day withdrawal right", beside "I have read and agree to the Terms of Service of yarrow.run".
- Compute credit is non-refundable as cash. Reserve before a run, debit actual cost, release the rest.
- USD only for now, integer cents.
- **Provider credit** (decided 2026-10-11). Sponsor credit is money Yarrow owes in compute; the compute itself is prepaid on Yarrow's own Anthropic and OpenAI accounts, and Stripe pays sponsor money out days after the providers charge. So:
  - both accounts reload themselves (the providers' own auto-reload, on the company card, with a monthly cap), set in their consoles, not in Yarrow;
  - when a provider still refuses for want of credit (Anthropic: "credit balance is too low", "API usage limits"; OpenAI: `insufficient_quota`), the run stops as `provider_out_of_credit`: the ticket goes back to the queue in its place (or the correction request, for a correction), it does not move to "stopped" on the builder's board, and its real cost, usually nothing, is charged as for any stop;
  - dispatch pauses (`provider_pauses`, one row per provider) and tries again every 30 minutes; a session that starts at that provider, or Resume in the admin, ends the pause. The founder gets one email per outage (Resend, from the brain, to `ALERT_EMAIL`).

## Work unit selection

- **A queue processed fast.** Tickets enter a queue and start as soon as money and provider rate limits allow. Runs execute in parallel.
- **Order: FIFO within each account, round-robin between accounts (organizations).**
  - When money is plentiful, this behaves like plain FIFO.
  - When money is scarce, it stops an account that enqueued thousands of tickets first from taking the whole pool. Waiting tickets start when new money arrives.
  - Creating several projects does not earn more turns.
- **Per-account concurrency limit** on sponsor-funded runs _(hypothesis: 5)_. It stops one account from draining the pool in a burst. It also keeps PRs at a pace owners can review and limits merge conflicts on the same repo.
- **Global concurrency** is bounded by provider rate limits, with backoff.
- A ticket is eligible for a sponsor's money only if its project matches that sponsor's filters.
- **No cost cap and no platform-side safety brake per ticket.** Heavy tickets are accepted. Runaway sessions are the providers' responsibility, since their harnesses have their own safeguards. Cost per run is still recorded in metrics, so anomalies are visible.
- **Correction requests** (`@yarrow-run <request>` on the PR):
  - unlimited;
  - each one is a normal run, funded the same way and with **no priority**;
  - it updates the same PR.
  - only a maintainer's comment that starts with the mention counts (owner, member, collaborator; never a bot);
  - every pull request says so, in one line above the footer: "Need a change? Comment `@yarrow-run` followed by what to change…" (decided 2026-10-11); so do the run page, to the project's members while the pull request is open, and /connect/terms before GitHub. A correction's commit is titled "Correction: …".

  Priority processing is a candidate for a later paid offer.

## Quality pipeline (free for everyone)

1. **Policy check:** the acceptable use policy is checked on the ticket and project description before any real spend.
2. **Implementation:** Opus implements the ticket with tests and lint.
   - Unclear-ticket path: Opus may flag the ticket as unclear instead of implementing it. Astra then re-reads the ticket.
   - If Astra also finds it unclear, the platform comments on the ticket asking for a better description, and the run ends as an abstention (`ticket_unclear`). The comment and the run's stop reason list one set of questions, Opus's (Astra's when Opus asked none): both agents ask the same things in their own words (decided 2026-10-08).
   - If Astra finds it clear, Opus proceeds with Astra's reading.
3. **Review:** Astra reviews the patch, systematically.
   - Astra classifies each comment as `blocking`, `suggestion` or `nit`. The review prompt is calibrated to be pragmatic, not pedantic.
   - Only `blocking` comments trigger Opus's **one fix round**.
   - The PR then opens.
   - **The fix round keeps the whole story** (decided 2026-10-23, after citron-clicker #3 on prod: the summary said only "Damaged saves are now refused" and the review only spoke of them). The implementer rewrites result.json as if its change had been right the first time: the summary stays the whole pull request (what the ticket asked, then what was done), a correction's summary what the correction changed. Astra's second look gets its first review: it checks each fix itself, then reviews the whole change, and its words tell the story in two or three sentences (what it checked, what it found at first, that it sent it back and it is fixed now), or what is still wrong, naming the cases that fail. Its JSON may list `unmet`, criteria the implementer ticked that the change does not deliver: the final review unticks them (✗ in Yarrow, ❌ on GitHub). No third round: what the fix round left broken shows as "Still to fix" in the description and as warnings in the panel.
   - Astra's final review is **in the pull request's own description**, under "Review by GPT Astra": its words, what is still to fix when the fix round was not enough, then at most three suggestions (nits are left out). No separate GitHub review is posted any more (decided 2026-10-10: it repeated the description). A correction's comment carries its review the same way.
   - The implement → review → fix loop is an internal brain module (`ReviewLoop`), with the maximum rounds and the severity threshold in config.

## Trust & safety

- An **acceptable use policy** applies to all projects, including hidden ones.
- The policy check classifies tickets and project descriptions. Flagged items go to human review: ticket text and description only, never code.
- The platform can suspend a project. Sponsors can report one.

Every meaningful action writes an append-only event in Postgres from day one. Dashboards come later.

- **Owners:**
  - signups, repos and trackers connected, tickets tagged;
  - time to first PR;
  - merge rate, time to merge, **rejection reasons**;
  - correction requests per PR;
  - unclear-ticket rate;
  - owners going inactive.
- **Runs:**
  - cost and duration per run, cost per merged PR, tokens and sandbox time per provider;
  - review: share of `blocking` comments, fix-round outcome;
  - abstention reasons, provider errors and rate-limit hits;
  - concurrency.
- **Sponsors:**
  - visit → sponsor conversion, average and repeat contribution;
  - time from payment to consumption;
  - filter usage;
  - sponsor board views.
- **Platform:** revenue (margin), pool balance, burn rate, days of activity left in the pool.

## Terminology

- Never "donation" / "don".
  - In France (and in many other countries), a "don" implies a gift to a qualifying non-profit, giving the right to a tax reduction and a tax receipt.
  - Yarrow is a commercial platform with a margin, and sponsors get visibility in return. Calling payments "dons" would be misleading.
  - For companies, sponsoring is usually a deductible advertising expense ("parrainage"). Confirm with an accountant.
- Use **sponsor**, **sponsoring**, **contribution** (code and ledger) and **compute credit**.

## Scope

**v1**
- Landing.
- Sponsor checkout (packs + custom amount). The profile form is the sponsor's own board row, edited in place, with the rank today for the amount chosen (decided 2026-10-07). Its logo tile is the upload button.
- Logos (sponsors and projects): the browser draws the file at 128 px (WebP, PNG fallback) and the server keeps it in Postgres (`images`, by SHA-256), served at `/images/<hash>.<ext>` with a one-year immutable cache. PNG, JPEG and WebP only, checked by their bytes; never SVG. A project without a logo shows its GitHub owner's avatar, on public projects only for the public boards (decided 2026-10-08).
- Sponsor dashboard with filters, including the hidden opt-in.
- The sponsor boards and the ticket column, on the landing.
- Add project: the GitHub App, plus **all four trackers** (GitHub Issues, Linear, Jira, Trello) behind one `TrackerAdapter` interface. The interface lists tagged tickets, reads a ticket, comments, and receives webhooks or polls.
- Public, Listed and Hidden tiers.
- Fair rotation per account.
- Two runners: Opus implements, Astra reviews (with one fix round), and the unclear-ticket double check.
- A narrated presentation of every pull request (the agent's screen, its voice, subtitles), questions while paused, then a live voice. Project run configuration and test secrets.
- Trust & safety basics.
- PR or abstention, with sponsor attribution, and correction requests on the PR.
- Login: GitHub for builders (Supabase Auth). Sponsors never need GitHub: Stripe Checkout collects the email, and the account is reached through an email sign-in link (decided 2026-10-06). A guest payment is held by a placeholder sponsor (`sponsor_profiles.guest`). The browser that paid is recognized at once by a signed HttpOnly cookie: back from Stripe, the guest lands on the Sponsor tab with no email to click; later payments from that browser add to the same row. The cookie only ever opens that guest's own sponsoring, never an account (Stripe does not verify emails). After each payment Yarrow sends its own thank-you email through Resend, with the sponsor's place and a one-time sign-in link for guests (Supabase admin link). **One person, one account** (decided 2026-10-12): someone signed in by email who then signs in with GitHub (Connect GitHub, or the sign-in page) gets GitHub **linked** to that account (Supabase manual linking, which must be on in each project's Auth settings), never a second account beside it: their sponsoring and their projects stay together, whatever email GitHub holds. If that GitHub account already has its own Yarrow account, the person is signed in to it instead (`identity_already_exists`). With manual linking off, GitHub signs in plainly, as before. The GitHub login is read from the linked identity until Supabase copies it into the user's metadata. Signing in (that link, the email form or GitHub) moves the guest's payments to the account, matched by verified email or by this browser's cookie; an existing profile is never renamed by someone else's payment (decided 2026-10-07). The Supabase "Magic Link" template points to `/auth/confirm?token_hash=…` so the link works on any device.
- Event log and metrics from day one.
- `Contribution → AgentRun → WorkUnit → Result` with reserve/debit/release.

**Later** (decided from metrics and feedback)
- **Removed cards** (noted 2026-10-10). A maintainer can delete the sponsors' card from a pull request's description; Yarrow cannot prevent it, and does not rewrite the description (`updatePullRequestBody` exists, nothing calls it). GitHub sends a `pull_request` event with `action: "edited"` and the previous body (`changes.body.from`) whenever the description is rewritten; the webhook already reaches Yarrow for merges and closes. When a card goes missing: warn the builder first; if it happens again, stop funding their projects (no card, no free compute). Build it once a real case shows up.
- A paid offer for owners, for example priority processing, owner top-ups and more powerful models.
- Separate handling of non-code tickets (analysis, architecture, ideation).
- **Best-of-two in parallel:** both providers implement the same ticket, and a judge keeps the better patch based on tests, acceptance criteria and cross-reviews. It costs about 2.2× on every ticket.
  - Ship it as an experiment flag, at first on tickets that triage marks as hard.
  - Keep it only if the merge-rate gain justifies the cost per merged PR.

  - A sponsor-created Claude routine pulling work from our MCP is parked until Anthropic confirms in writing that it fits "ordinary, individual usage".
  - The platform must never hold or trigger a sponsor's subscription credentials.
